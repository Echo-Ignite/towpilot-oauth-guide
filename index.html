Implementing OAuth 2.0 with TowPilot

TowPilot is an OAuth 2.0 authorization server. Your application can let TowPilot users sign in with their existing account and grant it scoped access to their data — the same mechanism that powers chat.towpilot.ai and AI agents connecting over MCP.

What you can build

  • Sign in with TowPilot — authenticate users without handling their credentials.
  • Scoped API access — call the TowPilot API on a user's behalf, limited to the scopes they approved.
  • AI agents over MCP — connect agents to the TowPilot MCP server with a user-authorized token instead of shared secrets.

Before you start

Every integration needs a registered client. Registration gives you a client_id and pins your exact redirect URIs. There are two tiers, and which one you have decides what your integration can reach:

  • Registered clients — set up by the TowPilot team. Only these may request full_access, the scope that unlocks the TowPilot API and the MCP data tools.
  • Self-service clients — the MCP endpoint also accepts dynamic client registration (RFC 7591), which most MCP-capable clients perform on their own. These are capped at openid email profile offline_access: they can sign a user in, but their tokens cannot read TowPilot data. If your integration needs data, ask for a registered client.
Browser and mobile apps are public clients. They never receive a client secret — the flow below relies on PKCE instead, which is mandatory for all clients.

The flow at a glance

TowPilot implements the standard Authorization Code flow with PKCE, plus one TowPilot-specific hop: the access token you receive is exchanged for a short-lived session JWT, and that is what the API authenticates.

Endpoint locations come from discovery metadata. Fetch it rather than hard-coding paths — they differ between the direct and MCP flows:

  • Direct API integrations — https://stytch.towpilot.ai/.well-known/openid-configuration
  • MCP clients — https://mcp.towpilot.ai/.well-known/oauth-protected-resource, which names the authorization server to use (RFC 9728). That server may be the MCP server itself rather than Stytch, so read the metadata per environment instead of assuming.

Step by step

  1. Send the user to authorize

    Generate a random state and a PKCE code_verifier/code_challenge pair, then redirect the user: 

    https://app.towpilot.ai/oauth/authorize
  ?client_id=YOUR_CLIENT_ID
  &redirect_uri=https://yourapp.example/callback
  &response_type=code
  &scope=openid email profile offline_access full_access
  &state=RANDOM_STATE
  &code_challenge=PKCE_CHALLENGE
  &code_challenge_method=S256

    The user signs in with their TowPilot account (or is already signed in) and sees a consent screen naming your app and the access it requests.

    Ask for the scopes you need. The advertised set is openid, profile, email, phone, offline_access and full_access. Two of them are load-bearing: full_access is required to reach the API at all (step 4), and offline_access is required to receive a refresh_token. Requesting full_access only works for registered clients — a self-service client gets the default set no matter what it asks for.

  2. Receive the code on your callback

    On approval, TowPilot redirects to your registered redirect_uri with ?code=…&state=…. Verify that state matches what you sent before doing anything else.

  3. Exchange the code for tokens

    POST the code and your PKCE code_verifier to the token_endpoint from your discovery metadata. For direct integrations that is: 

    POST https://stytch.towpilot.ai/v1/oauth2/token
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code
&code=AUTHORIZATION_CODE
&client_id=YOUR_CLIENT_ID
&redirect_uri=https://yourapp.example/callback
&code_verifier=PKCE_VERIFIER

    The response contains an access_token and, if you asked for offline_access, a refresh_token. MCP clients use the token_endpoint their own discovery metadata names, which is not necessarily this host.

  4. Exchange the access token for a session JWT

    The TowPilot API does not authenticate access tokens — it authenticates a Stytch session JWT (or a company API key). Trade one for the other: 

    POST https://app.towpilot.ai/api/auth/exchange
Authorization: Bearer ACCESS_TOKEN

    The response is {"session_jwt": "…"}. Only a full_access token can be exchanged; anything else is rejected here, which is where an under-scoped integration discovers it has no data access.

    Cache the session JWT. It lives about five minutes while the access token lives much longer, so hold the access token and re-exchange shortly before the session JWT goes stale. This endpoint is rate-limited (10 requests per minute) — exchanging per API call will trip it. The exchange is not idempotent: do not retry it blindly.

  5. Call the API

    GET https://app.towpilot.ai/api/…
Authorization: Bearer SESSION_JWT

    Authorization is resolved server-side on every request: the token identifies the user, and TowPilot determines what that user may reach. Tokens never embed roles or permissions, so access reflects the user's current standing — revoke a member, and their tokens stop working with them.

  6. Refresh when the access token expires

    POST https://stytch.towpilot.ai/v1/oauth2/token
Content-Type: application/x-www-form-urlencoded

grant_type=refresh_token
&refresh_token=REFRESH_TOKEN
&client_id=YOUR_CLIENT_ID

    This requires the offline_access scope on the original grant. Check grant_types_supported in the discovery metadata for the authorization server you are actually talking to — it differs between the direct and MCP flows. Refreshing yields a new access token, so exchange it again (step 4) for a session JWT.

Connecting AI agents over MCP

The TowPilot MCP server speaks the same OAuth. Point an MCP-capable client (Claude, or any agent runtime that supports OAuth for MCP) at: 

https://mcp.towpilot.ai/mcp

It discovers the authorization server from the protected-resource metadata, registers itself, walks the user through the same sign-in and consent, and receives a token scoped to that user.

  • No shared API keys — each agent connection is authorized by a real user.
  • Access is bounded by the user's own reach and the scopes they approved.
  • Revoking the user's grant cuts the agent off immediately.
Signing in is not the same as having access. A client that registered itself is capped at openid email profile offline_access, so its token cannot be exchanged for a session JWT and every data tool stays closed — the OAuth handshake succeeds and the first real call fails. Agents that need TowPilot data need a registered client (see Getting access).

Security requirements

RequirementWhy
PKCE, always Protects the code exchange even for clients that cannot hold a secret.
Exact redirect URIs Only URIs registered in advance are honored, matched exactly. Register every callback you use, including local development ones.
Exchange, don't improvise The API authenticates session JWTs, not access tokens. Keep the access token server-side and treat the exchanged session JWT as the short-lived credential.
Verify state Binds the callback to the session that started the flow (CSRF protection).
Tokens stay out of URLs Send access tokens only in the Authorization header.
Short-lived access tokens Plan for expiry; use the refresh grant rather than long-lived tokens.

Getting access

Anything that reads TowPilot data needs a registered client, and that is by request. Reach out to the TowPilot team with your application name, a short description, and your redirect URIs — you'll receive a client_id scoped for full_access and the discovery metadata for your environment.

Self-service dynamic registration is available at the MCP endpoint and needs no involvement from us, but it is sign-in only. Start there if all you need is identity; ask for a registered client the moment you need data.
